# CONTRIBUTING

Этот проект использует строгие правила коммитов и версионирования.
Нарушение этих правил приводит к сломанным релизам и хаосу в истории.

---

## Commit Rules

Используется стандарт **Conventional Commits**.

### Формат коммита

<type>(optional-scope): краткое описание

Описание должно чётко отражать суть изменений.

---

### Допустимые типы коммитов

- feat — новая функциональность
- fix — исправление бага
- refactor — рефакторинг без изменения поведения
- perf — оптимизация производительности
- docs — документация
- test — тесты
- chore — CI, конфиги, сборка, техдолг
- break — ломающие изменения (breaking changes)

---

### Примеры корректных коммитов

feat(client): add async product fetch
fix(handshake): fix token expiration bug
refactor(api): simplify dto mapping
break(api): change product dto structure

---

### Запрещённые коммиты

## Versioning

Проект использует **Semantic Versioning**.

Формат версии:

MAJOR.MINOR.PATCH

Пример:

2.4.1

Версия — это контракт совместимости.

---

### MAJOR

Увеличивается, если:
- нарушена обратная совместимость
- изменены публичные API или DTO
- удалены или переименованы публичные методы
- старый код может перестать работать

Пример:
1.9.3 → 2.0.0

---

### MINOR

Увеличивается, если:
- добавлена новая функциональность
- API расширен без поломки старого поведения
- существующий код продолжает работать без изменений

Пример:
2.3.4 → 2.4.0

---

### PATCH

Увеличивается, если:
- исправлены баги
- улучшена производительность
- проведён внутренний рефактор без изменения API

Пример:
2.4.0 → 2.4.1

---

## Release Rules

- Версия обновляется вручную
- Версия хранится в одном месте
- Каждый релиз обязан иметь git tag
- Каждый релиз обязан иметь changelog

Пример тега:

v2.4.1

---

## Final Rule

Если есть сомнения:
- не повышай MAJOR
- предпочитай MINOR
- PATCH используй только для фиксов
